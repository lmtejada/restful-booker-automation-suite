## 1. Folder structure

```
src/
├── clients/
│   ├── booking.client.ts     # BookingClient — every /booking call
│   └── auth.client.ts        # AuthClient — every /auth call
├── fixtures/
│   ├── api-clients.fixture.ts  # bookingClient / authClient (test-scoped)
│   ├── auth.fixture.ts         # authToken (worker-scoped)
│   └── index.fixture.ts        # merges both — the import every spec uses
├── test-data/
│   └── factories/
│       └── booking-data.factory.ts  # DEFAULT_BOOKING_DATA, generateBookingData, VALIDATION_SCENARIOS
├── types/
│   └── app.ts                # Booking, Nullable<T>, RequestOptions
├── utils/
│   ├── auth.ts                # DEFAULT_CREDENTIALS, getAuthToken, addAuthHeader
│   ├── config.ts              # getEnv
│   └── constants.ts           # BOOKING_PATH, AUTH_PATH
├── enums/                    # empty — add as needed
└── pages/                    # empty — unused, this is an API-only suite

tests/
├── api/
│   ├── functional/           # one spec per endpoint
│   └── integration/          # cross-endpoint flows
└── sanity.spec.ts            # framework/environment smoke check
```

**Why `functional/` and `integration/` are split:** `functional/` specs each own one endpoint and don't depend on state from another spec. `integration/` specs are `test.describe.serial` — a chain of steps that share state (a booking id, an auth token) across the whole lifecycle. Keeping them apart means a functional spec can run alone or in any order, while the serial ones are easy to spot as the exception.

**Why `clients/` is separate from `fixtures/`:** a client (`BookingClient`, `AuthClient`) is a plain class — no Playwright dependency beyond the `APIRequestContext` type. A fixture is what hands a _constructed_ client to a test. Keeping them apart means the clients are testable/importable outside Playwright's fixture system if that's ever needed, and each fixture file only has one job (wire up an instance, or manage a token).

## 2. Path aliases

| Alias          | Resolves to       |
| -------------- | ----------------- |
| `@fixtures/*`  | `src/fixtures/*`  |
| `@clients/*`   | `src/clients/*`   |
| `@utils/*`     | `src/utils/*`     |
| `@test-data/*` | `src/test-data/*` |
| `@app-types/*` | `src/types/*`     |
| `@enums/*`     | `src/enums/*`     |
| `@pages/*`     | `src/pages/*`     |

**Why:** avoids `../../../` relative imports as spec files get nested deeper under `tests/api/functional/` or `tests/api/integration/`.

**Gotchas:** both Playwright and ESLint need to resolve these independently — Playwright reads `tsconfig.json`'s `paths` natively (no extra loader), and ESLint needs `eslint-import-resolver-typescript` configured under `import-x/resolver` in `eslint.config.mts`. Add a new alias to `tsconfig.json` only, and both pick it up.

## 3. Tagging glossary

| Tag            | Meaning                                             | Script                                  |
| -------------- | --------------------------------------------------- | --------------------------------------- |
| `@smoke`       | Fast, must-pass-before-merge checks                 | `npm run test:smoke`                    |
| `@regression`  | Full functional coverage                            | `npm run test:regression`               |
| `@api`         | Every API-layer test (effectively all of them)      | `npm run test:api`                      |
| `@issues`      | Known-bug tests wrapped in `test.fail()` — see §8.4 | `npm run test:issues`                   |
| `@integration` | Cross-endpoint serial flows                         | no dedicated script — run via file path |

A test can carry more than one tag: `{ tag: ['@api', '@regression'] }`.

## 4. Fixtures and configuration

**Fixture dependency chain:**

```
@playwright/test's `test`
 ├─ api-clients.fixture.ts → adds bookingClient, authClient (test-scoped)
 └─ auth.fixture.ts        → adds authToken (worker-scoped)
       │
       └─ merged by mergeTests() into index.fixture.ts
              — the only fixture import a spec should use
```

`bookingClient`/`authClient` are constructed fresh per test from the per-test `request` fixture. `authToken` authenticates once per worker (its own `APIRequestContext`, independent of the per-test `request`) and retries once on failure.

Playwright resolves fixtures lazily: a test that only destructures `{ bookingClient }` never triggers the `/auth` call `authToken` would make, even though both come from the same merged `test` object. See §8.2 for why they're merged instead of one file extending the other.

**Environment selection:** `.env.<name>`, chosen by the `ENVIRONMENT` variable (defaults to `dev`, loading `.env.dev`). CI supplies variables through workflow `env:` blocks instead of a committed `.env` file.

**Reporters:** `list` (terminal) and `allure-playwright` (writes to `reports/allure-results`), both always on — no separate CI-only reporter.

**Notable non-default config** (`playwright.config.ts`):

| Setting          | Value                                   | Note                                                              |
| ---------------- | --------------------------------------- | ----------------------------------------------------------------- |
| `projects`       | one project, no `devices`/`browserName` | API-only suite — there's no browser matrix to run against         |
| `actionTimeout`  | 10000ms                                 |                                                                   |
| `expect.timeout` | 10000ms                                 |                                                                   |
| `trace`          | `retain-on-failure`                     |                                                                   |
| `workers` (CI)   | 1                                       | `test:ci` script; local runs use Playwright's default parallelism |

## 5. Naming conventions

- **Spec files:** one file per endpoint action — `booking-create.spec.ts`, `booking-retrieve.spec.ts`, `booking-update.spec.ts`, `booking-delete.spec.ts`, `auth.spec.ts` — plus `booking-validation.spec.ts` for the data-driven field-validation loop (§7).
- **Test titles:** the primary smoke test in each file is prefixed `[Smoke]` and carries the `@smoke` tag; every other title is a plain sentence describing the behavior under test. Titles aren't required to match a `TC-XXX` entry in `3. TEST-CASES.md` word-for-word — traceability for known bugs runs through the `test.fail()` comment (`BUG-XXX`) instead, not the title text.
- **Describe-block shape:** one top-level `test.describe(name, { tag: [...] }, () => {...})` per spec file, tags declared once at the describe level and inherited by every test inside, unless an individual test needs an extra tag (like `@issues`).
- **Client methods:** a typed, semantic verb (`create`, `getById`, `update`) for the common case, and the same name with `WithOptions` appended (`createWithOptions`) for the raw escape hatch. See §8.1.

## 6. Lint rules worth knowing

Only the rules that aren't obvious defaults, or that shape how a test gets written:

| Rule                                               | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@typescript-eslint/explicit-function-return-type` | Every fixture/client/helper function states its return type — makes `Promise<APIResponse>` vs. `Promise<void>` visible at the call site without hovering.                                                                                                                                                                                                                                                                                                                                                       |
| `import-x/order`                                   | Groups imports `builtin → external → internal → relative`, alphabetized within each group. `@fixtures/**` is pulled into the `external` group via an explicit `pathGroup` override (sorted after real packages like `@playwright/test`). Every other alias (`@clients/*`, `@utils/*`, `@test-data/*`, `@app-types/*`) has no override and lands in `internal` by the resolver's default classification — there's no rule specifically targeting `@clients`, it just isn't special-cased the way `@fixtures` is. |
| `func-style: declaration`                          | Top-level functions must use `function foo() {}`, not `const foo = () => {}`. Doesn't apply to inline callbacks (fixture bodies, test callbacks) — only to declared, named functions like the ones in `utils/`.                                                                                                                                                                                                                                                                                                 |
| `playwright/no-wait-for-timeout`                   | No hard waits — this is an API suite with no UI to wait on, so a hard wait almost always means masking a real race instead of fixing it.                                                                                                                                                                                                                                                                                                                                                                        |
| `playwright/prefer-web-first-assertions`           | Use `expect(response).toBe(...)`-style Playwright assertions over manual `if`/`throw`.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `no-console`                                       | No `console.log` left in committed specs; the one intentional exception (`console.warn` in `auth.fixture.ts`'s retry path) is suppressed inline with an eslint-disable comment, not a blanket rule change.                                                                                                                                                                                                                                                                                                      |
| `no-restricted-syntax` (custom)                    | Blocks `await` inside `expect(...)` — forces `await expect(x).resolves.toBe(y)` instead, so a rejected promise fails the assertion instead of throwing past it.                                                                                                                                                                                                                                                                                                                                                 |

## 7. Test data strategy

- **Static default:** `DEFAULT_BOOKING_DATA` (`booking-data.factory.ts`) — one `faker`-generated `Booking`, imported as-is by every test that just needs _a_ valid booking and doesn't care about its exact field values.
- **Generated, with overrides:** `generateBookingData(overrides)` spreads `DEFAULT_BOOKING_DATA` with the given overrides and returns a typed `Booking`. Use this instead of a manual `{ ...DEFAULT_BOOKING_DATA, field: value }` spread — same result, but it's the one place that spread logic lives.
- **Data-driven scenarios:** `VALIDATION_SCENARIOS` — an array of `{ description, overrides, expectedStatus, knownBug? }` — drives `booking-validation.spec.ts`'s loop. `MALICIOUS_PAYLOADS` is the same idea for injection-style inputs, looped over in `booking-create.spec.ts`.

**Rule of thumb:** a new field-level edge case (missing/null/wrong-type/wrong-range value) goes into `VALIDATION_SCENARIOS` unless it needs an assertion shape the loop can't express (a response header, a raw malformed body) — those become individual tests in the relevant spec file instead.

## 8. Conventions and decisions

### 8.1 API clients as Service Objects, with a typed method plus a raw escape hatch

**Rule:** every call to `/booking` or `/auth` goes through `BookingClient`/`AuthClient` (`src/clients/`), never a bare `request.post(...)` with a hardcoded path. Each client method comes in two forms: a typed, semantic one (`create(data: Booking)`, `login(credentials)`) that only accepts well-formed data and builds headers for you, and a `*WithOptions` counterpart (`createWithOptions`, `loginWithOptions`, `updateWithOptions`, `partialUpdateWithOptions`) that takes a raw Playwright request-options object with no shape checking.

**Why:** roughly 60 call sites duplicated the same endpoint paths and auth-header construction across every spec file before this existed. A single typed method can't cover every test, though — this suite deliberately sends malformed JSON, XML bodies, wrong `Content-Type`s, Basic Auth instead of a Cookie, both headers at once, an empty `{}` payload, and objects with extra fields the `Booking` type would reject via TypeScript's excess-property check. Forcing those through a strict `create(data: Booking)` either doesn't compile or can't express the request at all. The escape hatch keeps the endpoint path centralized even for those tests, without fighting the type system.

**How to apply:** reach for the typed method by default. Switch to `*WithOptions` the moment a test needs a header, body, or field the typed signature won't accept.

### 8.2 Fixture composition via `mergeTests`, not one file extending another

**Rule:** `api-clients.fixture.ts` and `auth.fixture.ts` are independent — neither imports the other. `index.fixture.ts` combines them with Playwright's `mergeTests()`, and every spec imports from `index.fixture.ts`, not from either fixture file directly.

**Why:** the alternative was having `auth.fixture.ts` extend `api-clients.fixture.ts` directly, so one `test` object carried everything. That works, but it means the auth fixture file has to know the clients fixture file exists. `mergeTests` combines two fixture files that were each built independently with a plain `base.extend()` off `@playwright/test`, so adding a third fixture module later doesn't require editing an existing one — it just gets added to the `mergeTests(...)` call.

**How to apply:** a new fixture is its own file, extending `@playwright/test` directly, then added to the `mergeTests(...)` list in `index.fixture.ts`. Fixture laziness is unaffected by how the `test` object was assembled — a test that only destructures `bookingClient` still never pays for `authToken`'s `/auth` call, confirmed by running the suite and checking auth call counts stayed at one per worker regardless.

### 8.3 Worker-scoped auth token, not per-test login

**Rule:** `authToken` authenticates once per worker process, not once per test. Specs that need it destructure `authToken` from `index.fixture.ts` alongside `bookingClient`; nothing calls `POST /auth` directly in a new test unless deliberately bypassing the shared token.

**Why:** logging in before every single test would mean one `/auth` call per test instead of one per worker — on a suite this size, most of those calls would be identical, redundant round trips against the shared public API. A worker-scoped fixture pays that cost once and reuses the token for every test the worker runs.

**How to apply:** any test that needs `PUT`/`PATCH`/`DELETE /booking/:id` auth destructures `authToken`. A test intentionally checking auth failure (malformed token, missing token, Basic Auth) still uses the client's normal `update`/`delete` methods — it just passes a bad or omitted token value instead of skipping the client.

### 8.4 The known-bug pattern: `test.fail()`, not `test.skip()`

**Rule:** for a confirmed Restful Booker defect, the test still asserts the _correct_ expected behavior, wrapped in `test.fail(true, 'Known bug — see docs/4. DEFECT-LOG.md (BUG-XXX)')`.

**Why:** skipping the test would hide the defect from every future run. `test.fail()` keeps the suite green (a `test.fail()`-wrapped test failing its assertion is itself a pass) while keeping the assertion honest — if Restful Booker ever fixes the bug upstream, that test starts unexpectedly _passing_, which Playwright reports as a failure of the `test.fail()` expectation. That failure is the signal to flip `knownBug` off and update the defect log, instead of the fix going unnoticed.

**How to apply:** verify the actual behavior first (a quick `curl`, don't assume), assert what a well-built API should return, wrap in `test.fail()` with the `BUG-XXX` id, then extend both `4. DEFECT-LOG.md` and `3. TEST-CASES.md` — the three cross-reference each other by id and need to stay in sync.

### 8.5 Docs are numbered by reading order, not creation order

**Rule:** files under `docs/` are prefixed `N. `, and the number reflects the order a new contributor should read them in, not the order they were written.

**Why:** this file (`2. TEST-FRAMEWORK.md`) was added after `TEST-CASES.md` and `DEFECT-LOG.md` already existed as `2.` and `3.`, but it makes more sense to read before either — understanding how the suite is built comes before reading individual test cases or defects. Both existing files were renumbered to `3.` and `4.` to make room, rather than appending this one as `4.` out of reading order.

**How to apply:** adding a new top-level doc means picking its position by what a reader needs first, and renumbering any files after it — check every cross-reference (`README.md`, `CLAUDE.md`, and the other docs) for the old filename when renumbering, since links are by filename, not just by number.

## 9. Decision log

**2026-08-28 — Fixture composition via `mergeTests`, not chained `.extend()`**
Considered having `auth.fixture.ts` extend `api-clients.fixture.ts` directly, so all fixtures lived on one `test` object through a single inheritance chain. Chose `mergeTests()` instead, keeping the two fixture files independent — see §8.2 for the reasoning.

**2026-08-28 — API Service Object pattern introduced (`BookingClient`, `AuthClient`)**
Every spec previously called `request.post('/booking', ...)`/`request.get(...)` directly, duplicating the endpoint path and auth-header construction across roughly 60 call sites. Replaced with `BookingClient`/`AuthClient`, exposed as fixtures. Considered routing every call, including deliberately malformed ones, through strictly-typed methods only — rejected because several existing tests need raw control over headers/body shape that a typed `Booking` parameter can't express (see §8.1's `*WithOptions` escape hatch).
