## 1. Folder structure

```
src/
├── clients/
│   ├── booking.client.ts     # BookingClient — every /booking call
│   └── auth.client.ts        # AuthClient — every /auth call
├── fixtures/
│   ├── api-clients.fixture.ts  # bookingClient / authClient (test-scoped)
│   ├── auth.fixture.ts         # authToken (worker-scoped)
│   └── index.fixture.ts        # merges both — the import every spec uses
├── test-data/
│   └── factories/
│       └── booking-data.factory.ts  # DEFAULT_BOOKING_DATA, generateBookingData, VALIDATION_SCENARIOS
├── types/
│   └── app.ts                # Booking, Nullable<T>, RequestOptions
├── utils/
│   ├── auth.ts                # DEFAULT_CREDENTIALS, getAuthToken, addAuthHeader
│   ├── config.ts              # getEnv
│   └── constants.ts           # BOOKING_PATH, AUTH_PATH
├── enums/                    # empty — add as needed
└── pages/                    # empty — unused, this is an API-only suite

tests/
├── api/
│   ├── functional/           # one spec per endpoint
│   └── integration/          # cross-endpoint flows
└── sanity.spec.ts            # framework/environment smoke check
```

**Why `functional/` and `integration/` are split:** Each `functional/` spec tests one endpoint on its own — it doesn't depend on any other spec running first. `integration/` specs are different: they're `test.describe.serial` chains that share state (a booking id, a token) across several steps. Splitting them apart makes the serial ones easy to spot as the exception, not the rule.

**Why `clients/` is separate from `fixtures/`:** A client (`BookingClient`, `AuthClient`) is a plain class. It only needs Playwright's `APIRequestContext` type — nothing else. A fixture's job is to hand a ready-made client to a test. Keeping the two apart means a client could be imported and tested outside Playwright's fixture system if that's ever needed. It also keeps each fixture file doing one thing: build an instance, or manage a token.

## 2. Path aliases

| Alias          | Resolves to       |
| -------------- | ----------------- |
| `@fixtures/*`  | `src/fixtures/*`  |
| `@clients/*`   | `src/clients/*`   |
| `@utils/*`     | `src/utils/*`     |
| `@test-data/*` | `src/test-data/*` |
| `@app-types/*` | `src/types/*`     |
| `@enums/*`     | `src/enums/*`     |
| `@pages/*`     | `src/pages/*`     |

**Why:** avoids `../../../` relative imports as spec files sit deeper in folders like `tests/api/functional/`.

**Gotchas:** Playwright and ESLint each resolve these on their own. Playwright reads `paths` straight from `tsconfig.json` — no extra setup needed. ESLint needs `eslint-import-resolver-typescript` configured under `import-x/resolver` in `eslint.config.mts`. Add a new alias to `tsconfig.json` only — both tools pick it up from there.

## 3. Tagging glossary

| Tag            | Meaning                                             | Script                                  |
| -------------- | --------------------------------------------------- | --------------------------------------- |
| `@smoke`       | Fast, must-pass-before-merge checks                 | `npm run test:smoke`                    |
| `@regression`  | Full functional coverage                            | `npm run test:regression`               |
| `@api`         | Every API-layer test (effectively all of them)      | `npm run test:api`                      |
| `@issues`      | Known-bug tests wrapped in `test.fail()` — see §8.4 | `npm run test:issues`                   |
| `@integration` | Cross-endpoint serial flows                         | no dedicated script — run via file path |

A test can carry more than one tag: `{ tag: ['@api', '@regression'] }`.

## 4. Fixtures and configuration

**Fixture dependency chain:**

```
@playwright/test's `test`
 ├─ api-clients.fixture.ts → adds bookingClient, authClient (test-scoped)
 └─ auth.fixture.ts        → adds authToken (worker-scoped)
       │
       └─ merged by mergeTests() into index.fixture.ts
              — the only fixture import a spec should use
```

`bookingClient` and `authClient` are built fresh for every test, from the per-test `request` fixture. `authToken` works differently: it logs in once per worker (using its own `APIRequestContext`, separate from the per-test `request`), and retries once if that login fails.

Playwright only runs a fixture when a test actually asks for it. A test that destructures `{ bookingClient }` never triggers the `/auth` call, even though `authToken` comes from the same merged `test` object. See §8.2 for why the two fixture files are merged instead of one extending the other.

**Environment selection:** the `ENVIRONMENT` variable picks which `.env.<name>` file loads (default: `dev`, so `.env.dev`). CI doesn't use a committed `.env` file — it sets variables through the workflow's `env:` block instead.

**Reporters:** `list` (prints to the terminal) and `allure-playwright` (writes to `reports/allure-results`). Both run every time — there's no separate reporter just for CI.

**Notable non-default config** (`playwright.config.ts`):

| Setting          | Value                                   | Note                                                              |
| ---------------- | --------------------------------------- | ----------------------------------------------------------------- |
| `projects`       | one project, no `devices`/`browserName` | API-only suite — there's no browser matrix to run against         |
| `actionTimeout`  | 10000ms                                 |                                                                   |
| `expect.timeout` | 10000ms                                 |                                                                   |
| `trace`          | `retain-on-failure`                     |                                                                   |
| `workers` (CI)   | 1                                       | `test:ci` script; local runs use Playwright's default parallelism |

## 5. Naming conventions

- **Spec files:** one file per endpoint action — `booking-create.spec.ts`, `booking-retrieve.spec.ts`, `booking-update.spec.ts`, `booking-delete.spec.ts`, `auth.spec.ts` — plus `booking-validation.spec.ts` for the data-driven field-validation loop (§7).
- **Test titles:** every title in `tests/api/**/*.spec.ts` starts with `[TC-XXX]: `, matching its entry in `3. TEST-CASES.md` — for example, `[TC-001]: valid credentials return a token`. The main test in each file also carries the `@smoke` tag, but its title doesn't repeat that as a `[Smoke]` bracket — the tag is enough on its own. See §8.6 for how this is enforced.
- **Describe-block shape:** one top-level `test.describe(name, { tag: [...] }, () => {...})` per spec file, tags declared once at the describe level and inherited by every test inside, unless an individual test needs an extra tag (like `@issues`).
- **Client methods:** a typed, semantic verb (`create`, `getById`, `update`) for the common case, and the same name with `WithOptions` appended (`createWithOptions`) for the raw escape hatch. See §8.1.

## 6. Lint rules worth knowing

Only the rules that aren't obvious defaults, or that shape how a test gets written:

| Rule                                               | Why                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `@typescript-eslint/explicit-function-return-type` | Every fixture, client, and helper function states its return type. You can see `Promise<APIResponse>` vs. `Promise<void>` at the call site, without hovering over it.                                                                                                                                                                                                    |
| `import-x/order`                                   | Sorts imports into four groups, in order: builtin, external, internal, relative — alphabetized within each. `@fixtures/**` is pulled into the `external` group on purpose (it sorts after real packages like `@playwright/test`). Every other alias — `@clients/*`, `@utils/*`, `@test-data/*`, `@app-types/*` — has no special rule and lands in `internal` by default. |
| `func-style: declaration`                          | Top-level functions must use `function foo() {}`, not `const foo = () => {}`. Doesn't apply to inline callbacks like fixture bodies or test callbacks — only to named, top-level functions such as the ones in `utils/`.                                                                                                                                                 |
| `playwright/no-wait-for-timeout`                   | No hard waits — this is an API suite with no UI to wait on, so a hard wait almost always means masking a real race instead of fixing it.                                                                                                                                                                                                                                 |
| `playwright/prefer-web-first-assertions`           | Use `expect(response).toBe(...)`-style Playwright assertions over manual `if`/`throw`.                                                                                                                                                                                                                                                                                   |
| `no-console`                                       | No `console.log` in committed specs. The one exception — a `console.warn` in `auth.fixture.ts`'s retry path — is allowed with an inline eslint-disable comment, not a change to the rule itself.                                                                                                                                                                         |
| `no-restricted-syntax` (custom)                    | Blocks `await` inside `expect(...)`. Use `await expect(x).resolves.toBe(y)` instead — that way a rejected promise fails the assertion, instead of throwing past it unnoticed.                                                                                                                                                                                            |

## 7. Test data strategy

- **Static default:** `DEFAULT_BOOKING_DATA` (in `booking-data.factory.ts`) is one `faker`-generated `Booking`. Tests import it as-is whenever they just need _a_ valid booking and don't care what's in it.
- **Generated, with overrides:** `generateBookingData(overrides)` takes `DEFAULT_BOOKING_DATA`, applies your overrides, and returns a typed `Booking`. Use this instead of writing `{ ...DEFAULT_BOOKING_DATA, field: value }` by hand — same result, but the spread logic lives in one place.
- **Data-driven scenarios:** `VALIDATION_SCENARIOS` is an array of `{ description, overrides, expectedStatus, knownBug? }` objects. `booking-validation.spec.ts` loops over it to generate one test per scenario. `MALICIOUS_PAYLOADS` works the same way, for injection-style inputs, looped over in `booking-create.spec.ts`.

**Rule of thumb:** a new field-level edge case — a missing, null, wrong-type, or out-of-range value — goes into `VALIDATION_SCENARIOS`. The exception: if it needs a check the loop can't express, like reading a response header or sending a raw malformed body, write it as its own test in the relevant spec file instead.

## 8. Conventions and decisions

### 8.1 API clients as Service Objects, with a typed method plus a raw escape hatch

**Rule:** Every call to `/booking` or `/auth` goes through `BookingClient` or `AuthClient` (`src/clients/`) — never a bare `request.post(...)` with a hardcoded path. Each client method comes in two forms: a typed one (`create(data: Booking)`, `login(credentials)`) that only accepts well-formed data and builds the headers for you, and a `*WithOptions` version (`createWithOptions`, `loginWithOptions`, `updateWithOptions`, `partialUpdateWithOptions`) that takes a raw request-options object with no shape checking.

**Why:** Before this existed, about 60 call sites repeated the same endpoint paths and auth-header code across every spec file. But one typed method can't cover every test — this suite deliberately sends malformed JSON, XML bodies, wrong `Content-Type` headers, Basic Auth instead of a Cookie, both headers at once, an empty `{}` body, and objects with extra fields the `Booking` type would reject. Forcing those through a strict `create(data: Booking)` either won't compile, or can't express the request at all. The `*WithOptions` escape hatch keeps the endpoint path in one place even for those tests, without fighting TypeScript.

**How to apply:** Use the typed method by default. Switch to `*WithOptions` as soon as a test needs a header, body, or field the typed signature won't accept.

### 8.2 Fixture composition via `mergeTests`, not one file extending another

**Rule:** `api-clients.fixture.ts` and `auth.fixture.ts` don't know about each other — neither imports the other. `index.fixture.ts` combines them using Playwright's `mergeTests()`. Every spec imports from `index.fixture.ts`, not from either fixture file directly.

**Why:** The alternative was having `auth.fixture.ts` extend `api-clients.fixture.ts` directly, so one `test` object carried everything. That works, but it means the auth fixture has to know the clients fixture exists. With `mergeTests`, each fixture file is built independently with a plain `base.extend()` off `@playwright/test`. Adding a third fixture module later doesn't mean editing an existing file — it just gets added to the `mergeTests(...)` call.

**How to apply:** A new fixture gets its own file, extending `@playwright/test` directly, then gets added to the `mergeTests(...)` list in `index.fixture.ts`. This doesn't cost anything extra: a test that only destructures `bookingClient` still never triggers `authToken`'s `/auth` call, no matter how the `test` object was put together. (Confirmed by running the suite and checking the auth call count stayed at one per worker.)

### 8.3 Worker-scoped auth token, not per-test login

**Rule:** `authToken` logs in once per worker process, not once per test. Specs that need it destructure `authToken` from `index.fixture.ts` alongside `bookingClient`. Nothing calls `POST /auth` directly in a new test, unless it's deliberately bypassing the shared token.

**Why:** Logging in before every single test would mean one `/auth` call per test, instead of one per worker. On a suite this size, most of those calls would be identical, wasted round trips to the shared public API. A worker-scoped fixture pays that cost once, then reuses the token for every test the worker runs.

**How to apply:** Any test that needs auth for `PUT`/`PATCH`/`DELETE /booking/:id` destructures `authToken`. A test that's checking auth _failure_ (a malformed token, a missing token, Basic Auth) still uses the client's normal `update`/`delete` methods — it just passes a bad or missing token instead of skipping the client.

### 8.4 The known-bug pattern: `test.fail()`, not `test.skip()`

**Rule:** For a confirmed Restful Booker defect, the test still checks for the _correct_ behavior — wrapped in `test.fail(true, 'Known bug — see docs/4. DEFECT-LOG.md (BUG-XXX)')`.

**Why:** Skipping the test would hide the defect from every future run. `test.fail()` does two things at once: it keeps the suite green — a `test.fail()`-wrapped test that fails its assertion counts as a pass — and it keeps the assertion honest. If Restful Booker ever fixes the bug, that test starts _passing_ unexpectedly, and Playwright reports that as a failure. That failure is your signal: turn off `knownBug` and update the defect log, instead of the fix going unnoticed.

**How to apply:** Check the real behavior first — a quick `curl`, don't assume. Assert what a well-built API _should_ return. Wrap it in `test.fail()` with the `BUG-XXX` id. Then update both `4. DEFECT-LOG.md` and `3. TEST-CASES.md` — all three cross-reference each other by id, and need to stay in sync.

### 8.5 Docs are numbered by reading order, not creation order

**Rule:** Files under `docs/` are prefixed `N. `. The number is the order a new contributor should read them in — not the order they were written.

**Why:** This file was added after `TEST-CASES.md` and `DEFECT-LOG.md` already existed as `2.` and `3.`. But it makes more sense to read first — understanding how the suite is built should come before reading individual test cases or defects. So the two existing files were renumbered to `3.` and `4.`, instead of tacking this one on as `4.` out of order.

**How to apply:** When adding a new top-level doc, pick its position by what a reader needs first, and renumber any files after it. Check every cross-reference — `README.md`, `CLAUDE.md`, and the other docs — for the old filename, since links point to filenames, not just numbers.

### 8.6 Test titles carry their `[TC-XXX]` id, enforced by lint

**Rule:** Every `test()` title under `tests/api/**/*.spec.ts` starts with `[TC-XXX]: ` — the id of its entry in `3. TEST-CASES.md`, followed by a colon and a space. `tests/sanity.spec.ts` is excluded, since it isn't part of the TC catalog. A smoke test's `@smoke` tag is enough on its own — titles don't also carry a `[Smoke]` bracket.

**Why:** The doc already linked tests back to their `TC-XXX` ids, through its "Automation reference" lines — but that link only lived in the doc. Nothing tied a test's _title_ to its case. So a renamed test, or a new one added without updating the doc, could drift out of sync silently. Putting the id in the title makes the link visible in the test runner's own output, not just in the doc.

**How to apply:** Enforced by `playwright/valid-title`'s `mustMatch` option, scoped to `tests/api/**/*.spec.ts` in `eslint.config.mts`. A missing or malformed `[TC-XXX]: ` prefix fails lint. The rule only checks the _pattern_ — it can't tell if the number is the _correct_ one for that test. Matching the right id to the right test is still a manual step, checked against `3. TEST-CASES.md` when you add or rename a test.

### 8.7 Ajv schema validation now, Pact contract testing deferred

**Rule:** Response shape validation uses `ajv` + `ajv-formats` (`schema-validation.spec.ts`, `src/test-data/schemas/`), not Pact. Pact stays on the roadmap as "not started" (see `README.md`'s Project Goals) rather than being added alongside it.

**Why:** Both can catch a response shape drifting from what's expected, but they solve different problems. Ajv validates _this specific response, right now_ — fast, in-process, no broker or coordination needed — which is exactly what's useful against a live API this suite doesn't own. Pact's real value is different: a consumer publishes its expectations to a broker, and the _provider_ verifies against them in their own CI before a breaking change ships. That's what actually prevents a break, instead of just detecting one after the fact. That provider-side verification step needs access to the provider's CI pipeline — not possible here, since `restful-booker.herokuapp.com` is a public demo API run by someone else, not a service this project's team controls. Adding Pact under those conditions would give contract _documentation_ value only, not the breaking-change-prevention value it's designed for — not worth the extra broker and tooling for a learning project against a third-party API.

**How to apply:** Use `ajv` schema validation (`compileSchema`/`formatSchemaErrors` in `src/utils/schema-validator.ts`) for any new response-shape assertion. Leave Pact as a documented future phase in `README.md` rather than building it here, unless the app under test ever changes to one this project's own team controls end-to-end (including its CI).

## 9. Decision log

**2026-08-28 — Test titles now start with their `[TC-XXX]` id**
Before this, a test's link to its `TC-XXX` case lived only in the doc — nothing in the code enforced it. Now every test title in `tests/api/**/*.spec.ts` starts with `[TC-XXX]: `, and a lint rule checks for it (`tests/sanity.spec.ts` is excluded, since it's not a documented test case). The alternative — leaving the link doc-only — was rejected: nothing would catch a title drifting out of sync with its TC entry until someone read the doc and compared by hand. See §8.6.

**2026-08-28 — Fixtures combined with `mergeTests`, not one file extending another**
Considered having `auth.fixture.ts` extend `api-clients.fixture.ts` directly, so every fixture lived on one `test` object through a single chain. Chose `mergeTests()` instead — it keeps the two fixture files independent. See §8.2 for why.

**2026-08-28 — `BookingClient`/`AuthClient` introduced (the Service Object pattern)**
Every spec used to call `request.post('/booking', ...)` or `request.get(...)` directly, repeating the endpoint path and auth-header code across roughly 60 call sites. Replaced with `BookingClient`/`AuthClient`, exposed as fixtures. Considered routing _every_ call — including deliberately malformed ones — through strictly-typed methods only, but rejected that: some tests need raw control over headers or body shape that a typed `Booking` parameter can't express. See §8.1's `*WithOptions` escape hatch.

**2026-08-31 — Ajv schema validation added; Pact contract testing stays deferred**
Considered adding Pact consumer-driven contract tests at the same time as the new `ajv`-based `schema-validation.spec.ts`, since both were candidates for verifying response shapes. Chose to only build the `ajv` layer for now: Pact's real value comes from the provider verifying a published contract in their own CI before a breaking change ships, and that verification step isn't achievable against `restful-booker.herokuapp.com` — a public demo API this project doesn't control the CI for. Building Pact here anyway would only get contract _documentation_, not the breaking-change-prevention it's designed for. Pact stays a documented, not-started phase in `README.md`. See §8.7.
