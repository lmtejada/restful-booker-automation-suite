## Functional & general defects

| ID      | Title                                                                                     | Severity  | Steps to reproduce                                                                                                                                                                                                                                                                                                                                                         | Linked TC      | Status  |
| ------- | ----------------------------------------------------------------------------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ------- |
| BUG-001 | Missing/null required booking fields (or an empty/absent body) cause a `500`, not a `400` | 🔴 High   | `POST /booking` with any of `firstname`, `lastname`, `totalprice`, `depositpaid`, `bookingdates`, `bookingdates.checkin`, or `bookingdates.checkout` omitted or `null`, an empty `{}` payload, or a completely absent body → API returns `500 Internal Server Error` with a plain-text body (no JSON, no error detail) instead of a `400` validation response.             | TC-008         | 🔴 Open |
| BUG-002 | Required name fields accept empty strings                                                 | 🟡 Medium | `POST /booking` with `firstname: ""` and `lastname: ""` → `200 OK`, booking is created with blank names instead of the request being rejected.                                                                                                                                                                                                                             | TC-008         | 🔴 Open |
| BUG-003 | Invalid booking dates are silently corrupted instead of rejected                          | 🟡 Medium | `POST /booking` with `bookingdates.checkin` or `bookingdates.checkout` set to a non-date string (e.g. `"invalid-date"`) → `200 OK`, and the stored/returned value is corrupted to the literal string `"0NaN-aN-aN"` instead of the request being rejected.                                                                                                                 | TC-008         | 🔴 Open |
| BUG-004 | `totalprice`/`depositpaid` are not validated for type, format, or range                   | 🟡 Medium | `POST /booking` with `totalprice: "one-hundred"` or `depositpaid: "yes"` → `200 OK`, wrong-typed value stored as-is. `totalprice: 99.5` → `200 OK`, but silently truncated to `99` (no rounding disclosure). `totalprice: -100` or `totalprice: 0` → `200 OK`, negative/zero price accepted. None of these are rejected with a `400`.                                      | TC-008         | 🔴 Open |
| BUG-005 | Illogical booking date ranges are accepted                                                | 🟡 Medium | `POST /booking` with `bookingdates.checkin` after `bookingdates.checkout` → `200 OK` instead of the request being rejected.                                                                                                                                                                                                                                                | TC-008         | 🔴 Open |
| BUG-006 | Unsupported Content-Type causes a `500`, not a `4xx`                                      | 🔴 High   | `POST /booking` with `Content-Type: application/yaml` or `text/plain` → `500 Internal Server Error` instead of `415 Unsupported Media Type` / `400 Bad Request`.                                                                                                                                                                                                           | TC-009         | 🔴 Open |
| BUG-007 | Updating/deleting a non-existent or already-deleted booking id returns `405`, not `404`   | 🟢 Low    | `PUT` / `PATCH` / `DELETE /booking/:id` for an id that does not exist (or was already deleted) → `405 Method Not Allowed` instead of `404 Not Found`.                                                                                                                                                                                                                      | TC-025, TC-028 | 🔴 Open |
| BUG-008 | XML responses are mislabeled as `text/html`                                               | 🟢 Low    | `POST /booking` or `GET /booking/:id` with `Accept: application/xml` → body is well-formed XML, but the `Content-Type` response header reads `text/html; charset=utf-8` instead of `application/xml`, breaking content-negotiation-aware clients that trust the header over sniffing the body.                                                                             | TC-007, TC-016 | 🔴 Open |
| BUG-009 | `checkin`/`checkout` query filters never match a booking against its own dates            | 🟡 Medium | `GET /booking?checkin=...&checkout=...` (combined, or `checkin` alone) using a booking's own exact `bookingdates.checkin`/`checkout` values never includes that booking in the results — reproduces on freshly created bookings _and_ long-standing pre-existing ones (verified against several), while `firstname`/`lastname` filters work correctly on the same records. | TC-012         | 🔴 Open |
| BUG-010 | Non-JSON Content-Type on `/auth` returns a misleading "Bad credentials"                   | 🟢 Low    | `POST /auth` with valid credentials but `Content-Type: text/plain` → `200 OK` with `{"reason":"Bad credentials"}` instead of a `415 Unsupported Media Type` (or `400`), misleading callers into thinking their username/password is wrong when the real issue is the request was never parsed as JSON.                                                                     | TC-003         | 🔴 Open |
| BUG-011 | Malformed date query filters are silently matched instead of rejected                     | 🟡 Medium | `GET /booking?checkin=08-25-2026` (wrong format, not `CCYY-MM-DD`) → `200 OK` with a small, seemingly arbitrary non-empty subset of bookings (not the full unfiltered list, not empty) instead of a `400 Bad Request`, meaning the server parses the malformed date into _something_ and matches on it.                                                                    | TC-018         | 🔴 Open |

_Not logged as defects: `additionalneeds` accepting `null`, an empty string, or special characters. That field is optional and free-text by design, so permissive handling there is correct behavior, not a flaw — covered by the same spec's remaining scenarios for regression coverage, not because anything is broken._
