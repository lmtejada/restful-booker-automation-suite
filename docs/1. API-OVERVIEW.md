## 1. What is this application

Restful Booker is a public, no-signup practice REST API for a fictional hotel booking system, built specifically for people to learn and demonstrate API test automation against. It is **not** a production system: there's no real persistence guarantee, no real payment or hotel behind it, and no isolated per-tester environment — everyone practicing against it shares the same live dataset on the same Heroku instance. That single fact explains most of what would otherwise look alarming: booking IDs and total counts drift constantly between test runs (other people's suites are creating and deleting records at the same time as yours), and there's no way to reset to a clean state before a run.

|                |                                                                                                                                                                                                                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **URL**        | `https://restful-booker.herokuapp.com`                                                                                                                                                                                                                                                                              |
| **Auth model** | Stateless token auth. `POST /auth` exchanges a hardcoded username/password for a token, used as either a `Cookie: token=<token>` header or an `Authorization: Basic <base64(username:password)>` header. Only required for `PUT`/`PATCH`/`DELETE /booking/:id` — creating and reading bookings need no auth at all. |
| **Data model** | A single resource, `Booking`: `firstname`, `lastname`, `totalprice`, `depositpaid`, `bookingdates: { checkin, checkout }`, and an optional `additionalneeds`. No relations, no pagination, no soft-delete — `DELETE` removes the record outright.                                                                   |

## 2. User accounts / roles

There is exactly one account, hardcoded by the API itself and stored in this repo as `ADMIN_USERNAME` / `ADMIN_PASSWORD` env vars. There are no roles or permission tiers — any caller who obtains a valid token can update or delete _any_ booking, not just ones they created.

---

## 3. Application map

Restful Booker has no UI or pages — the "map" here is the request flow between its endpoints:

```
POST /auth ──────────────► token
                              │
                              │ (Cookie or Authorization header)
                              ▼
POST /booking ──► GET /booking (list/filter) ──► GET /booking/:id ──► PUT/PATCH /booking/:id ──► DELETE /booking/:id
   (no auth)          (no auth)                     (no auth)              (auth required)          (auth required)
```

Creating and reading a booking are open to anyone; only mutating or deleting an _existing_ booking requires a token.

## 5. Looks like a bug, isn't a bug

**`POST /booking` requires no authentication.**
Anyone can create a booking with no token at all. This looks like a gap — a real hotel system would never let anonymous callers create reservations — but it's restful-booker's actual, documented design: only mutating or deleting an _existing_ booking is gated. Not something to flag; the test suite deliberately covers auth only on `PUT`/`PATCH`/`DELETE`.

**Non-numeric or non-existent booking ids return `404`, not `400`.**
`GET /booking/abc` and `GET /booking/999999` both return `404`. A stricter API might return `400` for a syntactically invalid id before even checking existence, but `404` ("nothing matches this identifier") is a defensible, common interpretation and the API is at least consistent about it — not logged as a defect.

**`firstname`/`lastname` query filters are case-sensitive.**
`?firstname=JIM` and `?firstname=jim` both fail to match a booking whose real name is `Jim`. Feels like it should be case-insensitive for a real search feature, but nothing in the API's contract promises that, and the behavior is at least consistent and predictable — documented, not logged as a bug.

**Unexpected extra fields in a request body are silently dropped.**
Sending `isAdmin: true` alongside a valid `POST`/`PUT`/`PATCH` payload succeeds and the extra field never appears in the response. This is actually the _safe_, correct behavior for an API to have (no accidental privilege escalation via extra JSON keys) — confirmed deliberately, not a defect.

**`PUT` with an empty `{}` body returns `400` and leaves the booking untouched.**
Could easily be mistaken for "PUT wipes the resource if you don't send everything" — verified it does neither: the request is rejected outright and the original booking is unchanged.

**A fake `Authorization` header alongside a _valid_ `Cookie` token still succeeds.**
`PUT`/`PATCH` accept the request as long as _one_ of the two supported auth mechanisms is valid, even if the other one present is garbage. This is a support-multiple-auth-methods design decision (an inclusive-OR check), not a security hole introduced by this API's specific implementation — but worth knowing if you're debugging why a "clearly wrong" header didn't cause a rejection.

**Total booking counts and ids drift between test runs.**
Because the environment is a single shared public instance (see §1), the total number of bookings and which ids are "old" vs "new" changes constantly from other people's concurrent test runs — not something wrong with this test suite or the API. Tests are written to check for the presence of a just-created fixture rather than asserting on absolute counts, specifically to stay robust against this.

## 6. Future work

- **Response schema validation** — no test currently asserts full response _shape_ (field presence/types, no unexpected extras) for `POST`/`GET`/`PUT`/`PATCH` responses or the `/auth` token response.
